# First-time setup for this repo

Test content lives in `testdata/` — one file per test, plus a small
manifest. It is generated by the test-bank repo's pipeline, never
hand-written.

```
testdata/manifest.js       loaded at startup; one entry per test
testdata/202606asiav1.js   the full test, fetched only when a sitting
testdata/202512usav1.js    starts or resumes (202512usav1 is a STUB)
```

1. Run the app: serve the folder over HTTP (`python3 -m http.server`) and
   open `index.html`. **A `file://` copy cannot lazy-load tests** — browsers
   block the fetch — so use a local server, or build the single-file
   preview below, which has every test inlined.
2. `python3 assemble.py` builds `dist/index-live.html`: one self-contained
   file with all test content inlined, for the claude.ai preview panel.
3. `node build-site.js` assembles the deploy directory `_site/`. It ships
   only the allowlisted app files plus every test the manifest lists.

## Adding a test

1. Convert it in the test-bank repo (`tsv_to_bluebook_json.py`).
2. Write `testdata/<testId>.js`, which registers the test:
   `window.__TESTDATA__ = window.__TESTDATA__ || {};`
   `window.__TESTDATA__["<testId>"] = { …, testVersion: "YYYY-MM-DD-x" };`
   `testId` follows the source-PDF convention `YYYYMM+region+v#`
   (e.g. `202606asiav1`) and is internal — students only see `testName`.
3. Add its entry to `testdata/manifest.js` (testId, testName, testVersion,
   moduleCount, questionCount, sections).
4. Rebuild. `build-site.js` **fails the build** if the manifest lists a test
   with no file, so a typo surfaces as a red build rather than a 404 in a
   student's browser.

Renaming a test's `testId` orphans existing attempt records, which are keyed
`attempt:<testId>:…`. If you must rename one, list the old id in that test's
`legacyIds` so records, resume-lookup and the dashboard still resolve.

## Remote backend (Supabase) — Phase H

Optional. Without it the app runs in **local mode** exactly as before, so a
fresh clone needs no setup at all.

**1. Create the schema.** In the Supabase SQL editor, run
`supabase/schema.sql`. It is idempotent, so re-running is safe. It creates the
`records` KV table, enables RLS with **no anon policies**, grants the
`authenticated` role full access, and creates the four student RPCs.

**2. Create your tutor login.** Authentication → Users → add a user with your
email and a password. That account is what the dashboard signs in with.

**3a. Point the app at the project — locally.** Copy `config.example.js` to
`config.js` and fill in:

```js
window.ACESTEM_CONFIG = {
  SUPABASE_URL: "https://YOUR-PROJECT-REF.supabase.co",
  SUPABASE_ANON_KEY: "sb_publishable_..."   // or a legacy anon key
};
```

`config.js` is gitignored and is **never** committed or inlined into
`dist/index-live.html` — `assemble.py` skips it and aborts the build if any
key-shaped value reaches the output.

**3b. Point the app at the project — on Netlify.** Because `config.js` is
gitignored it is not in the deploy checkout, so `netlify.toml` runs
`node gen-config.js` at build time to generate it. Set these two variables
under **Site configuration → Environment variables**:

| Variable | Value |
|---|---|
| `SUPABASE_URL` | `https://<your-ref>.supabase.co` |
| `SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` (or set `SUPABASE_ANON_KEY` for a legacy JWT key) |

If either is missing, malformed, or still a placeholder, **the build fails**
rather than deploying — a config-less deploy would come up in local mode and
silently record to each browser instead of syncing, which is invisible until
someone notices results never reach the dashboard. The generator also refuses
a `sb_secret_…` / `service_role` key outright, since that would bypass RLS in
the browser. It never prints the key into the build log.

The build then runs `node build-site.js`, which copies **only** the files the
running app needs into `_site/` — the published directory. Internal files
(design docs, specs, `assemble.py`, the build scripts, `reference/`,
`supabase/`, `tests/`) are never deployed, so no URL can reach them in any
capitalisation. `_headers` is copied in because it only works inside the
publish directory.

**If you add a file the app needs, add it to `ALLOW` in `build-site.js`.** The
build fails if `index.html` references a file that isn't allowlisted, so a
forgotten entry shows up as a failed deploy instead of a 404 for a student.

This replaced an earlier attempt to block internal paths with redirect rules.
That approach cannot work: Netlify matches redirect `from` paths
case-sensitively but serves files case-insensitively, so
`/tests/injection-proof.js` 404'd while `/TESTS/injection-proof.js` returned
200 and served the file.

You can run the generator locally too:
`SUPABASE_URL=… SUPABASE_PUBLISHABLE_KEY=… node gen-config.js`

For a deliberate local-mode deploy, delete the `[build]` section from
`netlify.toml`.

Both Supabase key generations work: the current `sb_publishable_…` and the
legacy JWT anon key. The app talks to PostgREST directly with `fetch`, so
there is no supabase-js version to keep in step.

**Never put the `sb_secret_…` / service_role key anywhere in this repo.** It
bypasses RLS. The publishable/anon key is safe in the browser *only* because
anon has no table privileges.

**4. Signing in.** Students use their `AS-XXXXXXXX` code as before. You sign
in by typing your **email** into the same box — that opens the tutor password
prompt. The old `acestem-admin` name is disabled whenever a remote backend is
configured.

**5. Migrating existing local records.** If a device recorded attempts in
local mode, open the dashboard on that device, sign in as tutor, and use
**⬆ Upload local records to server**. It skips keys already on the server, so
running it twice is harmless.
